# Implementation and adoption

New Critical work uses the [four-round Critical workflow](critical-four-rounds.md). The v8 procedures below cover Direct, Standard and replay of runs already recorded under the earlier profile.

`STAGED_NOT_INSTALLED`. Read this package for authorized evaluation. Existing runs keep their recorded profile. Operational profile selection requires its own decision and evidence.

## Local evaluation

1. Identify the exact source and archive. Keep installed, frozen baseline, and staged controller identities distinct. Preserve the installed workflow.
2. Exercise the [runtime](runtime.md) phases and record shapes in disposable fixtures. Retain actual command, source, result, and evidence identities.
3. Give a neutral read-only evaluator the staged entrypoint or one assigned role prompt with a small task. Observe whether it identifies the role, lane, next supported action, and limits without access to the broader workstream.
4. Verify the qualified local worker mode and offline GitHub adapter against the frozen package. Retain independent implementation reviews in separate evidence tied to that candidate.

## Minimum probe set

| Probe | Required observation |
|---|---|
| Prompt forward exercise | Each role selects a lawful next step and reports limits with bounded context |
| Route examples | Urgent trivial work can be Direct. High risk selects Critical. Unknown risk holds writes |
| High finding and handoff | Sol owns the affected repair on new runs. Reassessment may change lane or lead |
| File expansion | An eligible path is observed before write, with exact RED on the expanded candidate. Excluded paths are refused |
| Phase and coverage | Real named Python and Node results qualify. Lifecycle assertions, skipped or filtered results, and missing aggregate acceptance block behavioral coverage. A changed test starts a new cycle |
| Original witnesses | Withdrawal of selected original approval or decision support invalidates dependent GREEN and worker production. Unrelated support withdrawal leaves valid proof available |
| Worker replacement | A prior worker and child cannot affect replacement or integration output. Revoke while the native fetch is active and observe refusal with unchanged integration files, refs, and objects |
| Admission recovery | Exact pending retry after revocation records the observed effect without replay. Unchanged full state gives `NO_EFFECT`. An object-only or torn import gives `PARTIAL` and holds dependent work |
| Batch change | Delegated removal checks initial and observed owned paths against their first baseline and preserves continuation. Prerequisite removal requires replanning |
| Source and target changes | A changed head or target holds delivery until current combined proof qualifies. Local authority or candidate drift during the final provider read refuses PUT |
| Lost acknowledgment | Intended, no effect, unintended, and unknown outcomes remain distinct |
| Cleanup | A fully accounted never-dispatched synthetic clone can be removed while a durable integration ref retains the predecessor. Lost retention or uncertain writers hold removal |
| Failure learning | Preserve first failure evidence. Repeated routine failure promotes with its original output |
| Legitimate completion | A valid narrow repair and a clean Direct task can finish |

Use deterministic checks where possible. Assess unsafe cases with precise source evidence. Record tested bounds and limits. Formal methods remain optional for consequential state properties, with reachable success and explicit environment assumptions.

## Exploratory trial

After actual authorization, start with a bounded non-P0 feasibility exercise. Keep assurance and model routing fixed while testing stronger receipts and clearer prompts. Design approval supplies design evidence.

After selecting the relevant proposed policy, use up to ten suitable real tasks for an exploratory comparison. Select tasks whose authority, risk, checks, and adapter capability qualify. Test Direct reviewer reduction independently of model routing and batching. Compare the same frozen candidate and acceptance against baseline shadow audits. Freeze verdicts before sharing findings or repairing the candidate.

Record one row per attempted task with lane, candidate, acceptance, sessions, wall time, actual findings, later defects, interventions, and usage when available. Include interruptions, repairs, and batch waiting. Separate shadow costs from the proposed steady-state route.

Set unacceptable outcomes and stopping rules before the trial. A material missed defect or unsupported completion stops advancement of the affected route. A small sample can establish feasibility and expose faults. Adoption-grade evaluation requires owner-selected thresholds, representative workload, severity definitions, independent adjudication, and held-out cases.

## Profile selection

Activation requires an exact compatible implementation, current independent assurance, qualified operational model and tier transport, any selected live delivery target, explicit `tier_policy`, trial evidence appropriate to the use, owner selection, and a recovery path. Native v1 certification remains `BLOCKED_NOT_CERTIFIED`. Local package verification keeps the candidate `STAGED_NOT_INSTALLED`.

Keep max effort, distinct finding rechecks, and the at-most-five-ticket cap. Lower effort, original-finder closure, broader Direct eligibility, and general cross-candidate reuse remain deferred.
